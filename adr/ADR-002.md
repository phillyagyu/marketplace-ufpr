# ADR-002: Persistência Desacoplada via Padrão Repository e Modelo de Domínio Rico

## Status
Aceito

## Contexto
O sistema possui regras críticas: não é permitido que um usuário contrate a si mesmo (RES01) e horários não podem sofrer *overbooking* (RES02). Para garantir que o comportamento da aplicação atenda ao atributo de testabilidade (ASR-03), a validação dessas regras não pode ocorrer dentro do banco de dados (via *triggers* ou *constraints*) nem depender de servidores ativos.

## Alternativas consideradas
1. **Validação no Controller ou no Banco de Dados:** Acopla as regras de negócio a frameworks HTTP ou dialetos SQL, impedindo testes isolados.
2. **ORM Ativo (Active Record):** As entidades de negócio herdam de classes de persistência, misturando comportamento e acesso a dados (violando o Princípio da Responsabilidade Única - SRP).
3. **Modelo de Domínio Rico + Padrão Repository:** Entidades puras em memória validam suas próprias regras. A persistência é delegada a repositórios que implementam interfaces.

## Decisão
Utilizar um **Modelo de Domínio Rico combinado com o padrão Repository**. As próprias entidades (ex: `Servico`, `SlotDisponibilidade`) aplicarão o padrão *Information Expert* (GRASP) para validar mudanças de estado. A persistência será abstraída pelas portas `ServicoRepository` e `ContratacaoRepository`, permitindo plugar adaptadores SQLite ou Em Memória.

## Consequências
* **Benefícios:** A arquitetura garante que é impossível criar um estado inválido no sistema (ex: reservar horário ocupado). Permite a execução de testes unitários ultrarrápidos em memória, isolando o domínio.
* **Custos e Riscos:** Adiciona esforço de desenvolvimento, pois exige escrever código de mapeamento (*Data Mapper*) para converter tuplas do banco SQLite em objetos Python e vice-versa.
